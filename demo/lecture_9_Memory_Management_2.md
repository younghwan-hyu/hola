## 페이지 테이블의 구조 (Structure of the Page Table)

- 세 가지 접근: 계층적 페이징 (Hierarchical Paging), 해시 페이지 테이블 (Hashed Page Tables), 역 페이지 테이블 (Inverted Page Tables).

## 2단계 페이지 테이블 (Two-Level Page-Table Scheme, 계층적 페이징)

- 문제: 프로그램의 주소 공간이 큼.
  - 32비트 주소, 4KB(=2^12) 페이지 크기라면 (m=32, n=12): m−n = 20 → 2^20 (100만) 개의 논리 페이지.
  - 페이지 테이블 엔트리 100만 개. 엔트리당 4바이트면 페이지 테이블 크기 4MB (2^22 바이트).
  - 4MB 페이지 테이블을 저장하려면 프로세스당 1K(=2^10)개의 페이지 프레임 필요.
- 해결:
  - 전체 페이지 테이블을 디스크에 저장.
  - 페이지 테이블 자체를 페이지 단위로 필요할 때(on-demand) 로드 → 페이지 테이블을 위한 페이지 테이블이 필요.
- 2단계 페이징 예 (32비트 머신, 4K 페이지):
  - 논리 주소 = 페이지 번호 20비트 + 페이지 오프셋 12비트.
  - 페이지 테이블이 페이징되므로 페이지 번호를 다시 분할: 10비트 페이지 번호 p1 (외부 페이지 테이블 인덱스) + 10비트 페이지 오프셋 p2 (내부 페이지 테이블 페이지 안에서의 변위).
  - 논리 주소 구조: | p1 (10비트) | p2 (10비트) | d (12비트) |
  - p1은 outer page table의 인덱스, p2는 inner page table 페이지 내 변위. (Forward-mapped page table)

## 다단계 페이징과 성능 (Multilevel Paging and Performance)

- 더 큰 주소 공간에는 (B-tree처럼) 3번째 페이지가 데이터 블록이 아니라 다음 레벨 페이지 테이블이 됨.
- 각 레벨이 메모리에 별도 테이블로 저장되므로, 논리→물리 주소 변환에 3~4번의 메모리 접근이 필요할 수 있음.
- 메모리 접근 시간이 5배가 되어도 TLB 덕분에 성능은 합리적으로 유지됨:
  - 4단계 페이징에서 TLB 히트율 98%라면: EAT = 0.98 × 120 + 0.02 × 520 = 128 나노초 — 메모리 접근 시간 대비 28% 저하에 불과 (TLB 접근 20ns, 메모리 접근 100ns 가정).
- 그래도 64비트 주소에는 6단계 페이징이 필요해 부적절 → 현재 64비트 OS들은 주소에 48비트만 사용: 4단계 페이징.

## 해시 페이지 테이블 (Hashed Page Tables)

- 32비트보다 큰 주소 공간에 사용.
- 가상 페이지 번호를 해시해 페이지 테이블에 매핑. 이 페이지 테이블은 같은 위치로 해싱되는 원소들의 체인(chain)을 가짐.
- 체인에서 가상 페이지 번호를 비교하며 일치를 찾고, 찾으면 해당 물리 프레임을 추출.

## 역 페이지 테이블 (Inverted Page Table)

- 문제: 왜 페이지 테이블이 그렇게 큰가?
  - 페이지 테이블 크기는 페이지 수에 비례 — "논리" 페이지마다 엔트리 하나.
  - 그러나 한 시점에는 적은 수의 페이지만 필요 (memory resident).
- 해법: "물리" 페이지 프레임마다 엔트리 하나를 두자.
  - 각 페이지 테이블 엔트리는 process-id를 포함.
  - 시스템 전체에 페이지 테이블 하나 — 필요한 엔트리 수는 페이지 프레임 수. 모든 프로세스가 이 테이블을 공유.
- 단점: 전체 테이블을 검색해야 함. 페이지 공유가 불가능.
- 보완: 해시 테이블로 검색 범위 제한 (메모리 조회 1회 추가), TLB로 가속.

## 세그먼테이션 (Segmentation)

- 메모리에 대한 사용자의 관점(user view)을 지원하는 메모리 관리 기법.
- 프로그램은 가변 길이 세그먼트(segment)들의 모음. 세그먼트는 논리적 단위: main(), 함수, 전역 변수, 스택, 심볼 테이블, 배열 등.

### 세그먼테이션 구조 (Segmentation Architecture)

- 논리 주소 구조: <segment-number, offset> 2차원.
- 세그먼트 테이블 (segment table): 2차원 논리 주소를 물리 주소로 매핑. 각 엔트리:
  - base: 세그먼트가 메모리에 상주하는 시작 물리 주소.
  - limit: 세그먼트의 길이.
- STBR (Segment-table base register): 세그먼트 테이블의 메모리 위치를 가리킴.
- STLR (Segment-table length register): 프로그램이 사용하는 세그먼트 수. 세그먼트 번호 s는 s < STLR일 때 합법.
- 하드웨어: s로 세그먼트 테이블을 찾고, offset d < limit 검사 후 base + d로 물리 주소 생성.

### 보호와 공유 (Protection & Sharing)

- 보호: 세그먼트 테이블 각 엔트리에 valid/invalid 비트 (0 = 불법 세그먼트), R/W/X 비트를 연관.
- 공유: 보호 비트가 세그먼트에 붙으므로 코드 공유가 세그먼트 수준에서 발생. 공유 세그먼트는 각 프로세스에서 같은 세그먼트 번호를 가져야 함 (자기 참조 코드가 세그먼트 번호+오프셋으로 자신을 참조하기 때문).
- 할당: 세그먼트 길이가 가변이므로 메모리 할당은 동적 저장 공간 할당 문제 — first fit / best fit. 외부 단편화는 있지만 내부 단편화는 없음.

## 페이징을 결합한 세그먼테이션 (Segmentation with Paging)

- 세그먼트를 페이징함으로써 외부 단편화 문제 해결.
- 순수 세그먼테이션과의 차이: 세그먼트 테이블 엔트리가 세그먼트의 base 주소가 아니라 그 세그먼트를 위한 페이지 테이블의 base 주소를 담음.
- 가상 주소 형식: v = (s, p, d) — 세그먼트 번호 s, 페이지 번호 p, 변위 d.
- 주소 변환: s로 세그먼트 테이블에서 페이지 테이블을 찾고, p로 그 페이지 테이블에서 프레임을 찾은 뒤 d를 더함. TLB를 함께 사용해 가속.
